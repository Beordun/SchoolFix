# 1\. Understand the admin/bursar's job

According to the SchoolFix PRD, the School Administrator/Bursar is responsible for five core activities\:

1. Configuring classes and class arms.
2. Allocating teachers to classes.
3. Setting up school fee schedules.
4. Verifying incoming payments.
5. Reviewing financial audit records.

Unlike the parent portal, which focuses on an individual child's experience, the admin portal should provide a **school-wide operational overview**\.

The design should prioritise three things\:

- **Visibility\:** What's happening across the school?
- **Action\:** What needs the administrator's attention?
- **Accountability\:** Can every important financial action be traced?

The PRD specifically emphasises audit trails, reliable tuition reconciliation and strict financial consistency. fileciteturn3file3

## Why these sections matter

**School overview cards**

The administrator needs a quick understanding of the school's size and configuration. The most useful initial indicators are active students and configured class arms.

**Financial overview**

The bursar needs to know how much the school expects to collect, how much has been verified and what remains outstanding.

The PRD defines the balance calculation as\:

\[
\text{Balance}=\text{Expected fees}-\text{Verified payments}
\]

Payment attempts must not be counted as verified collections. fileciteturn3file1

**Needs your attention**

This is the most actionable part of the dashboard. It should bring outstanding work to the administrator instead of making them search for it.

**Recent activity**

Show transaction reference, payment method, amount, timestamp and status. Clicking a transaction should open its full record.

# 7\. Visual design and responsive behaviour

I recommend a clean, professional SaaS interface.

- Light neutral backgrounds.
- White or slightly elevated content cards.
- One primary brand colour for navigation and primary actions.
- Green for verified payments.
- Amber for pending items.
- Red for failed transactions.
- Grey for abandoned or inactive records.

The dashboard should be desktop-first for administrative work, but responsive enough to use on a budget Android phone.

| Component | Desktop | Mobile |
|--------|--------|--------|
| Navigation | Persistent sidebar | Drawer |
| Summary cards | 4 across where space permits | 2 across |
| Transaction list | Data table | Stacked cards |
| Filters | Inline toolbar | Expandable filter panel |
| Charts | Wider visualisations | Simplified summaries |
| Actions | Standard buttons | Larger touch targets |

Avoid heavy charts, oversized animations and unnecessarily complex tables. SchoolFix is designed for schools operating with constrained hardware and connectivity. fileciteturn3file5

## 9\. Three details to settle before high-fidelity design

There are three points I would not silently assume\:

1. **Administrator versus bursar\:** The PRD groups them into one persona and defines an `ADMIN` role. Should the same account handle all administrative and financial operations, or should you have separate administrator and bursar permissions?
2. **Teacher allocation\:** Should a teacher be assigned to an entire class arm only, or should subject-teacher assignments also be supported?
3. **Student management\:** Will administrators register and edit student records directly, or will student enrolment be handled through another workflow?

My recommendation is to design the first version around the existing `ADMIN` role, class-arm teacher assignments and direct administrative access to student records, but keep the screens flexible if your completed backend supports more granular permissions.

**My strongest recommendation\:** Start with the admin dashboard and payment verification screens. Together, they establish the visual foundation and the most important operational workflow in SchoolFix.

## Why these sections matter

**School overview cards**

The administrator needs a quick understanding of the school's size and configuration. The most useful initial indicators are active students and configured class arms.

**Financial overview**

The bursar needs to know how much the school expects to collect, how much has been verified and what remains outstanding.

The PRD defines the balance calculation as:

\[
\text{Balance}=\text{Expected fees}-\text{Verified payments}
\]

Payment attempts must not be counted as verified collections. <FileCite ref_id="turn3file1" />

**Needs your attention**

This is the most actionable part of the dashboard. It should bring outstanding work to the administrator instead of making them search for it.

**Recent activity**

Show transaction reference, payment method, amount, timestamp and status. Clicking a transaction should open its full record.

The detailed transaction view should show:

- Student and parent information.
- Class and academic term.
- Submitted amount.
- Payment channel.
- Bank or gateway transaction reference.
- Supporting evidence, if available.
- Previous verified payments for the student and term.
- Verification action.

Verification should require a deliberate confirmation. Once approved, the backend should record the verified payment, verifier identity and timestamp.

This workflow is central to SchoolFix's financial audit model. <FileCite ref_id="turn3file1" />

# 7. Visual design and responsive behaviour

I recommend a clean, professional SaaS interface.

- Light neutral backgrounds.
- White or slightly elevated content cards.
- One primary brand colour for navigation and primary actions.
- Green for verified payments.
- Amber for pending items.
- Red for failed transactions.
- Grey for abandoned or inactive records.

The dashboard should be desktop-first for administrative work, but responsive enough to use on a budget Android phone.

| Component | Desktop | Mobile |
|---|---|---|
| Navigation | Persistent sidebar | Drawer |
| Summary cards | 4 across where space permits | 2 across |
| Transaction list | Data table | Stacked cards |
| Filters | Inline toolbar | Expandable filter panel |
| Charts | Wider visualisations | Simplified summaries |
| Actions | Standard buttons | Larger touch targets |

Avoid heavy charts, oversized animations and unnecessarily complex tables. SchoolFix is designed for schools operating with constrained hardware and connectivity. <FileCite ref_id="turn3file5" />

## 9. Three details to settle before high-fidelity design

There are three points I would not silently assume:

1. **Administrator versus bursar:** The PRD groups them into one persona and defines an `ADMIN` role. Should the same account handle all administrative and financial operations, or should you have separate administrator and bursar permissions?
2. **Teacher allocation:** Should a teacher be assigned to an entire class arm only, or should subject-teacher assignments also be supported?
3. **Student management:** Will administrators register and edit student records directly, or will student enrolment be handled through another workflow?

My recommendation is to design the first version around the existing `ADMIN` role, class-arm teacher assignments and direct administrative access to student records, but keep the screens flexible if your completed backend supports more granular permissions.

**My strongest recommendation:** Start with the admin dashboard and payment verification screens. Together, they establish the visual foundation and the most important operational workflow in SchoolFix.
